# REDCap Import Guide - HEARTLAND Template v1.0.2

These are draft import-rehearsal instructions, not a verified compatibility claim for a REDCap version.
The institution's administrator must confirm the supported CSV/project XML/instrument ZIP workflows
in its target instance. Do not assume that a general ODM-style XML is accepted by an instrument ZIP uploader.

**Local candidate hold, 24 September 2026:** the converter fix preserves both bounds, but target import,
calculation/branching behavior and CSV/XML equivalence remain untested. The CSV's ESSI bounds/note
divergence still requires adjudication; the checked-in XML and other derivatives were not regenerated
as an approved release. Do not move this candidate into patient use or a production collection project.
Any authorized rehearsal uses synthetic data in a separate nonproduction project, with preserved
import reports and a record of exact source versions. Software test success is not clinical approval.

## Path A — Data Dictionary CSV (recommended)

1. **Create an empty project.** REDCap Home → *New Project* → Name it (e.g. "HEARTLAND Validation — Site X"), Purpose = *Research*, storage location per your IRB.
2. **Open the Data Dictionary upload page.** In your new project, go to *Project Setup* → *Design your data collection instruments* → **Upload data dictionary (CSV)**.
3. **Upload the file.** Select `instruments/heartland_data_dictionary.csv` from your local copy of the repository.
4. **Review the preview if available.** Record actual form counts, errors and warnings, including those for `bl_risk_score`, `bl_risk_tier` and `gdmt_classes_count`. The intended five forms and calculations are acceptance criteria, not observed import results. Stop on unresolved discrepancies.
5. **Apply only in the authorized nonproduction project.** Preserve the preview report and source checksum before confirming the upload using the target instance's verified controls.
6. **Enable the repeating instrument.** *Project Setup* → *Enable optional modules and customizations* → toggle **Repeatable instruments and events**. Then click *Modify*, mark `monthly_followup` as repeating, save.
7. **Stop at nonproduction validation.** Record imported variables, both bounds, calculations, branching and repeating behavior. Production or real-data use is outside this rehearsal and requires separate clinical, institutional and privacy authorization.

### Troubleshooting Path A

- **"Variable name exceeds 26 chars":** check the row where it errors; rename carefully (keep leading prefix). This template ships with all names ≤25 chars.
- **Calc field parse error:** copy the formula shown in `variable_definitions.md` exactly; watch for smart-quote pasting.
- **Branching logic parse error:** REDCap expects `[field] = "1"` (with double quotes). If your CSV was opened in Excel and re-saved, smart quotes may have been introduced — re-download from GitHub.

## Path B — XML instrument

This path is unverified. Ask the target instance administrator which project XML or instrument package
format is accepted before uploading; the menu labels below are historical instructions, not a newly
verified UI procedure or an assertion that this simplified XML will import.

1. **Create an empty project** (same as Path A step 1).
2. **Confirm the import route.** An instrument ZIP uploader is not proof that raw XML is supported. Obtain the administrator's accepted format and procedure; do not rename XML to ZIP or bypass validation.
3. **Select an identified candidate only if that format is supported.** Record the file path, checksum and target version. Do not assume the older checked-in XML includes the local fixes.
4. **Inspect the result.** Record actual form and field counts and all validation messages. The intended five forms are a comparison target, not a verified outcome.
5. **Enable repeating instrument** (same as Path A step 6).
6. **Keep the test project nonproduction.** Preserve the import report and verify actual structure/behavior; do not infer equivalence or patient-use authorization.

### Troubleshooting Path B

- **"Invalid ODM document":** `xmllint --noout` checks XML well-formedness only, not ODM schema conformance or REDCap compatibility. Preserve the target's error and ask its administrator how to validate the supported format.
- **Unrecognized extensions:** preserve the error; do not remove metadata to force an import. A CSV rehearsal is a separate path requiring its own validation, not a demonstrated equivalent fallback.

## After import — verify with sample data

1. Go to *Data Import Tool* (left sidebar).
2. Upload `examples/sample_data.csv` in **dry-run** mode.
3. Record actual row counts and errors and compare them with the selected sample file. No zero-error result or imported row count has been demonstrated in this update.
4. Do **not** commit the sample data to a production project — it is synthetic, seeded with fixed random numbers, and will contaminate any real cohort.
5. In a separate synthetic fixture, verify import/export precision for fractional values (e.g. 4.5, 150.5 and 12.5), both bounds, missing values, calculations and branching. The converter omits unsupported precision metadata; it does not prove how REDCap will store or display the values.

## What to customize for your site

Fields that commonly need local adjustment before go-live:

| Field | Why adjust |
|-|-|
| `facility_name` choices | Restrict to a drop-down of your site list |
| `rural_urban` mapping | Some sites prefer raw RUCA 1-10 rather than the collapsed 4-bucket version |
| `gdmt_*_target` defaults | Your formulary may bound titration differently |
| PRO instruments beyond KCCQ-12 | Add any your IRB has already approved |

For protocol-level customization (e.g. a research-only subset of variables), see `docs/validation_study_protocol.md`.
